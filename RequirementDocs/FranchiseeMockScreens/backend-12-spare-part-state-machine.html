1. The request state machine

The technician only raises a request. Facility staff log every other step. The machine is P4 with one ruling added: a facility may cancel an approved request (approved → rejected, reason required), so a part that can never be supplied no longer needs a force-close to clear it.

    Home franchisee has no fallback (R4). A technician whose franchisee has no active facility admin or operator cannot raise a request (409 NO_FACILITY). Company Admin and National Head cannot work the queue, but they can create facility users for the home franchisee (Facility users page, "Add facility admin"). The facility queue they open shows no home queue.
    A wrong step is 409 PART_REQUEST_BAD_STATE: "This request is already approved - refresh to see where it is." Two facility users racing: one wins.
    Facility actions are allowed whatever the ticket's status (D6): an old pump comes back on Friday, after the job is Awaiting Customer. Only the status recompute is conditional - it runs only while the ticket is Awaiting Part.
    The technician cannot cancel in Awaiting Part (cancel is Assigned-only). Exits from a stuck wait: the facility rejects, or a manager force-closes.
    Speed clock: every move into or out of Awaiting Part is a status_changed event with exact from / to, which is how task 11 subtracts the wait.

    4. The inherited catalogue

    Parts sit on category nodes (any level, root included) and on product models. A ticket's list is every part on its node path root first plus its model's own; the same name at several levels shows once, deepest wins; an inactive deeper row hides the name inherited from above (D11). The ticket here is a Service call for the model Acme FL-7 (7 kg).
