Mocks the whole programme. Index of every mock for 00-index.md and its 19 task docs (00-18), built from 16-rollout-and-docs.md for the release order. Where a task doc and the index disagree, the index wins.

How to use these mocks

  • Static and click-through only. No framework, no build, no server: open any file by double-click. Nothing is saved and nothing calls the API.
  • Screens (tasks 07, 08, 09, 13, 14, 15) show layout and states. Explainers (backend tasks 00-06, 10-12, 16) show the rules with small interactive demos, because those tasks have no screen.
  •  A dashed outline  marks wording that is PROPOSED and needs owner sign-off (index section 7) before the client task is built.
  • The owner has settled ten of the open questions and the mocks show the settled behaviour; five remain open (below, and in full on the test and rollout page). Figures in the demos come from the worked examples in the task docs.

Owner decisions

Settled (10), shown in the mocks: speed clock starts at the later of accept and slot start · an approved part request can be cancelled (rejected with a reason) · the last active admin of a non-home franchisee cannot be deactivated · home parts have no Admin / NH fallback, and a franchisee with no parts desk cannot raise requests · type changes refused with open jobs or a redeemable balance · vendor price hidden from franchise users · no speed money on force-close · staff see both travel and speed on any ticket in scope, never a non-home base's coordinates or pool · a technician may self-set the base and the admin can correct it · no travel estimate on the offer.
Still open (5):
  • PINCODE_OUTSIDE_FRANCHISEE status code: 422 (current) or 400
  • Facility admin and facility operator share part powers (the admin also manages operators)
  • A franchisee admin sees its tickets read-only
  • Employee force-close payout is ignored, not refused
  • A reversal lands in the month it is written, on statements

Release gates

00-index.md section 4 lists six lettered gates (a, b, b2, c, d, e), shown here in full.

(a) Mobile before API moneyTask 07 is on Play (production track) before Tasks 10-12 are published. Index 6a sharpens it: and at least 90% of active technicians are on that build.
(b) Prod migrated firstEach migration runs on RelianceProdDB (by the owner) before the API that needs it is published.
(b2) Tasks 01-03 togetherPublished together, immediately after prod is migrated to 5d2a8c6e0b13: once the five franchisee_id columns are NOT NULL, the old API cannot raise tickets, add technicians, close jobs or take redemptions.
(c) Copy signed offThe PROPOSED copy of a client task is signed off before that task is built.
(d) 08 never without 09Once an Admin can create a franchisee-admin login, that person can sign in; without the portal they would land in the staff shell.
(e) Console learns the new kindsThe console's ledger kind labels ship no later than the API writing travel / speed_* (it renders an unknown kind as NaN).
